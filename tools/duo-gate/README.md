# duo-gate: scripted, fail-closed gate collector (milestone M2.0)

Runs the Duo 1 two panel gates of `docs/gate-m1.md` (plan sections 6 and 16.4) over adb, records preconditions and
evidence, asserts on machine-readable state, and reports **PASS / FAIL / INCOMPLETE** per check with counts. Python
standard library only; runs on Windows and Linux with `uv`. The tool drives the device only through adb and the DuoProbe
app (`tools/duo-probe`, version `gate-2` or later).

## Fail-closed rules

- **PASS** only when every required repetition was performed and evidenced and every assertion held.
- **FAIL** when evidence contradicts the contract (wrong panel, wrong task, input delivered to the other task, leak
  while locked, crash). A definite failure is reported even if other evidence is missing.
- **INCOMPLETE** for everything else: missing or late events, a log marker that never arrives (capture not live),
  parser mismatch, unknown identity or several candidate tasks, lost adb connection, fewer repetitions than required,
  skipped steps, tool errors.
- Evidence for an action is only taken between its own unique log markers (`DuoGate: mark id=<run>.<n>`), so earlier
  events (stale evidence) can never satisfy a check. Dumps are taken after the action settled, inside the bracket.
- **Real input receipt**: taps and typed text are generated by the tool; the probe logs the touches (`event=touch`,
  raw display coordinates) and the sentinel tokens (`event=text sentinels=dgs<8 hex>`) it received. The intended task
  must log them and the other task must not; a missing focus event is never taken as proof.
- **Manual checks never PASS.** Operator-performed or operator-observed steps (physical folds, real Recents / hinge-edge
  / predictive-Back gestures, lit-panel identity, animation containment) are guided with prompts and evidence is
  collected around them; machine evidence or an operator "no" can make them FAIL, otherwise they stay INCOMPLETE
  "manual review required" for a reviewer. A gate verdict is computed over its automated checks; the report counts the
  manual checks pending review separately.
- Expected geometry is literal Duo 1 data (display 2784x1800, panel A `[0,0][1350,1800]`, panel B
  `[1434,0][2784,1800]`), never computed by the code under test. The preflight checks the panel areas against it.

## Requirements

- adb on `PATH` (or `--adb` / `$ADB`), one device (or `--serial`), USB debugging authorised.
- The panel image (`sys.duode.panels.active=1`), unfolded, both panels lit, rotation 0. `wm size` must have no
  override (a single-screen posture is refused).
- DuoProbe **gate-2** or **gate-3** installed (`dumpsys package org.duode.probe` shows the `versionName`). It adds the touch/text
  sentinel and `targets` events and *Probe test 2 (own task)*; an older probe stops the run at preflight. Rebuild and
  install it as in `tools/duo-probe/README.md` (`adb install -r` works over the system copy).
- `uv` (any Python >= 3.10 it provides). No packages are installed.
- G6: a secure screen lock set by the operator (PIN or password; a pattern needs `--g6-unlock manual`).
- Gesture navigation (`navigation_mode=2`) for the scripted Back swipes (G4) and the cross-focused Home swipe (G2).

## Running

From the repository root (Windows PowerShell or a Linux shell alike):

```sh
uv run --no-project python tools/duo-gate/duo_gate.py list                 # gates and what they cover
uv run --no-project python tools/duo-gate/duo_gate.py preflight            # record + check preconditions; changes nothing
uv run --no-project python tools/duo-gate/duo_gate.py run                  # default set: G1 G2 G4 G5 G6 G9, 10 reps
uv run --no-project python tools/duo-gate/duo_gate.py run G1 G2 --reps 3   # selected gates
uv run --no-project python tools/duo-gate/duo_gate.py run all --allow-reboot   # every gate incl. guided ones and PO
uv run --no-project python tools/duo-gate/duo_gate.py restore ~/duogate-evidence/duogate-<run>   # after an interrupted run
uv run --no-project python tools/duo-gate/duo_gate.py restore ~/duogate-evidence/duogate-<run> --reboot   # also reboot if the panel properties had to be restored
uv run --no-project python tools/duo-gate/duo_gate.py report ~/duogate-evidence/duogate-<run>    # re-render report.md
```

Options for `run`: `--reps N` (>= 1, default 10; 0 or negative is rejected), `--settle S` (max seconds to wait for an expected event, default 8),
`--screens key|all|none`, `--no-input` (no prompts: manual steps stay INCOMPLETE; a closed stdin, e.g. no terminal,
behaves the same: end of input is "skip"), `--posture-confirmed` (also for `preflight`: operator assertion that the
device is unfolded, both panels lit, rotation 0; needed when the posture prompt gets no answer, otherwise the preflight
is INCOMPLETE), `--allow-reboot` (PO),
`--g6-unlock pin|manual`, `--launcher-app` (G1L, default Calendar), `--quickstep` (Launcher3 HOME component for G1L/G3),
`--keep-settings` (skip restoration), `--out DIR` (default `~/duogate-evidence`, outside the repository), global `--serial`, `--adb`.
Exit code: 0 PASS, 1 FAIL, 2 INCOMPLETE, 3 usage error.

## What a run does

1. **Preflight** (recorded in `preconditions.json` before anything changes; `restore.json` written first): build
   identity (`ro.build.display.id`, incremental, `ro.duode.*`), probe/Launcher3/SystemUI paths, SHA-256 of the probe
   APK, `services.jar`, `framework.jar`; both panel properties, `sys.duode.panels.active` and the panel areas actually
   present; HOME; Recents component; IME (default, enabled, `show_ime_with_hard_keyboard`, recorded only); navigation
   mode; density;
   physical/override size; display offset; committed device state; rotation settings; secure-lock credential type
   (only the type is stored); operator confirmation of the dual posture (prompt, or `--posture-confirmed`; unanswered
   -> INCOMPLETE); keyguard state, checked before anything drives the UI. A showing keyguard is the specific
   INCOMPLETE reason: with no secure lock `run` dismisses it (wake + `wm dismiss-keyguard`, recorded in
   `preconditions.json` as `keyguard`, nothing restored for it), `preflight` only reports it; with a secure lock the
   operator unlocks on screen and runs again. The preflight verdict is only printed once every preflight step finished;
   any tool error there is INCOMPLETE.
2. **Test settings** (recorded, restored at the end): `stay_on_while_plugged_in=7`, `accelerometer_rotation=0`,
   `user_rotation=0`, HOME = `org.duode.probe/.ProbeHomeActivity`. IME settings are never changed
   (`show_ime_with_hard_keyboard` stays at the device's value: forcing it could mask IME defects; a keyboard that does
   not appear on the first tap fails G5).
3. **Gates** in order G1, G1L, G2, G4, G5, G6, G3, G7, PO, G9 (only those selected). Probe test tasks are removed
   between setups (`am stack remove`, verified in the dumps).
4. **Restore** (in a `finally`: also after errors, a lost device or Ctrl-C; probe task cleanup is best-effort and
   cannot skip it) settings, HOME and both panel properties, and read them back. Panel properties are only changed by
   PO, which restores and reboots itself; if they (or the boot's `sys.duode.panels.active`) still differ from the
   recorded state, they are restored and the result stays INCOMPLETE "reboot required" unless `--allow-reboot` (or
   `restore --reboot`) authorizes the reboot, after which panel mode is verified. The expected mode is the recorded
   `active` value (records from before it existed: `preconditions.json`, else derived from the recorded properties with `SystemProperties.getBoolean` semantics:
   `1/y/yes/on/true` on, `0/n/no/off/false` or unset off, anything else unknown),
   so a pending reboot is never forgotten between two `restore` runs; an unknown mode is never reported complete.
5. **Report**: `report.md`, `results.json`, console summary.

### Gates

| Gate | Scripted (automated, can PASS) | Guided (manual, never PASS) |
|---|---|---|
| G1 | `G1.launch.A/B`: N taps on *Probe test* per side from the probe home (launch, then reuse after Home): `launch` event side/label, same task id on reuse, `onResume` bounds = panel, task under `Panel0Tasks`/`Panel1Tasks`, `mode=fullscreen`, not policy-hidden. `G1.launch0.A/B`: same with *Send launchDisplayId=0*. `G1.crossReuse`: the one *Probe test* task follows taps on alternating panels. `G1.amStartDisplay0`: `am start --display 0` (not from home) lands in `DefaultTaskDisplayArea`, fullscreen, display bounds. | `G1.freeformRequest`: `am start --windowingMode 5`, placement recorded (policy undefined until M2.5). |
| G1L | | `G1L.A/B` (operator taps the `--launcher-app` icon in Launcher3 on the named panel): task placement/mode/reuse, and the tap side verified from the launch intent's source bounds (wrong side -> INCOMPLETE). Machine-verified, but operator-performed, so never PASS. |
| G2 | `G2.home.A/B`: focus the panel by a tap on its probe (touch receipt + WM/input focus), Home key: `Home: minimizing PanelN` names that panel only, its task gets the policy flag (8), the other task stays placed, visible, not stopped (pauses recorded), and takes a tap. `G2.restore.A/B`: relaunch reuses the same task, `Restored minimized`, not hidden. `G2.crossHome.A/B`: focus the *other* panel by a tap, then a Home swipe from this panel's bottom edge, without a preparatory tap; same assertions. If the synthetic swipe is not taken as a gesture, that attempt stays INCOMPLETE. | `G2.crossHomeManual.A/B`: created only when the synthetic swipe was not recognized; the operator performs the real gesture, same assertions (can FAIL, never PASS). |
| G4 | `G4.back.A/B`: focus the other panel by a tap, Back swipe from this panel's outer edge: this task pauses and stops, the other does not, stays placed and visible; Back on the probe home fails. | `G4.hingeBack.A/B` (hinge-side edge), `G4.backCancel.A/B` (predictive Back cancelled: no lifecycle change; operator confirms the animation stayed in the panel). |
| G5 | `G5.ime.*` (A editor 1, A editor 2, A->B, B->A with one tap, F10): tap receipt; editor focus; latest insets non-zero for the target; latest insets of the other task zero (`imeVisible=true` with zero insets is accepted, F10 correction); `ImeContainer` bounds and requested-bounds = target panel; IME input/layering/control targets = the target task's window; a typed sentinel reaches the target editor only. `G5.otherTouchable`: the other panel takes a tap with the keyboard up. `G5.rotate`: rotate 90 (settings; completion and display rotation verified as in G7), bring the keyboard up again in the relaunched probe, keyboard confined to the target's panel area, areas do not overlap, both tasks back on their panels after rotating back. | `G5.foldKeyboard`. |
| G6 | Three phases (ordinary tasks on both panels; *Probe locked* (showWhenLocked) on A; on B), N lock cycles each: power off/on, then an attempted tap on the ordinary task. `G6.locked.*`: keyguard showing; every ordinary task window explicitly `isOnScreen=false` and `isVisible=false` (unreported visibility or no window -> INCOMPLETE); not touchable in the input dispatcher; WM focus and the input dispatcher's focused window (checked independently; missing or unresolvable -> INCOMPLETE) not on an ordinary task (the dispatcher's FocusedApplications is recorded as a diagnostic only: keys go to the focused window); no `onResume`/touch/text/editor focus in an ordinary task. `G6.unlock.*`: keyguard gone, task ids and panels kept. `G6.occlusion.swlA/B`: functional F8 (showWhenLocked occludes and is on screen). The PIN is asked once (not echoed, never written: redacted in `commands.log`) and typed only when the focused window belongs to SystemUI; the first failed unlock stops G6 (no blind retries). `--g6-unlock manual` lets the operator unlock on the device instead; `G6.unlock.*` are then manual checks (never PASS). | |
| G3 | | Overview open/select/cancel from each panel with the probe HOME and Quickstep: invariants (no task lost, no stranded policy flag), the selected task's panel (contract: the invoking panel; F7 currently moves it to the default area = FAIL), cancel keeps both tasks in place; operator answers on visibility and scope. |
| G7 | `G7.rotate`: rotations 90/180/270 and back to 0 in dual posture, each completed by action-scoped probe events (`rotation=<n>` after the marker) and the display rotation read from `dumpsys window displays` (not reached -> INCOMPLETE): tasks keep their panel area by name, task bounds = area bounds, areas do not overlap, both tasks back on their panels at 0. | `G7.fold.A/B` (N folds per side: invariants folded and after unfolding, `wm size`, device state and posture composition logged, operator confirms the lit panel shows its own task, F6), `G7.homeFoldRelaunch` (P1b). |
| PO | Needs `--allow-reboot`: both panel properties to 0, reboot, `sys.duode.panels.active=0`, no `Panel*` areas, probe launches from each side land fullscreen in `DefaultTaskDisplayArea` with display bounds; then the recorded properties are restored, reboot, geometry checked again. A locked device after reboot is handed to the operator. `persist.sys.*` needs `adb root`. | |
| G9 | `G9.noCrash`: dropbox `system_server_*`, `system_app_*`, `SYSTEM_TOMBSTONE` entries newer than the run start, plus captured `AndroidRuntime` / `ActivityManager` crash and ANR lines: system_server or SystemUI -> FAIL; other apps recorded. | |

### Must stay manual (plan 16.4)

Lit/dark panel identity, physical folds and sensor timing, real hinge-edge and predictive gestures, Recents gestures,
secure-lock interaction by the operator (`--g6-unlock manual`), visual animation defects, accessibility usability, soak.
The tool prompts for them and collects dumps, screenshots and log windows, but cannot mark them passed.

## Evidence directory

`<out>/duogate-<YYYYmmdd-HHMMSS>-<hex>/`:

| File | Content |
|---|---|
| `preconditions.json`, `restore.json` | recorded state; `restore.json` is written before the first change |
| `logcat.txt` | captured log, **allowlisted tags only** (`DuoGate`, `DuoProbe`, `DuoDisplayAreaPolicy`, `DuoDisplayMask`, `POSTURE PROCESSOR`, and crash/ANR levels of `AndroidRuntime`, `ActivityManager`, `InputDispatcher`, `WindowManager`, `DEBUG`, `libc`) |
| `snaps/NNNN-<step>-<kind>.txt` | `dumpsys activity containers`, `activity activities`, `window displays`, `window windows`, `input` per step |
| `screens/*.png` | screenshots (captured on the device and pulled; `--screens`) |
| `extra/` | dropbox dumps; with the uiautomator fallback only the probe home control names and bounds (the raw hierarchy is never stored, and is deleted from the device) |
| `commands.log` | every adb command with return code and duration (secrets redacted) |
| `operator.log` | prompts and answers (secrets recorded only as entered/empty) |
| `results.json`, `report.md` | per check: status, pass/fail/incomplete counts of the required repetitions, reasons, notes, evidence links |

The probe never logs editor contents: only the sentinel tokens it finds and the text length.

## Not covered yet (stay INCOMPLETE or absent)

- Transition containment (G8): no WM/Shell/SurfaceFlinger trace capture; final screenshots cannot prove containment.
- Explicit TaskDisplayArea launches, external displays, process death/restart, and a `configChanges` app (rotation or
  fold with a surviving IME target, frameworks 0015).
- Restoration of app state/back stack beyond task identity (the probe has a single activity per task).
- Recents automation (synthetic swipes cannot open Overview).

## Format assumptions (each one fails closed if wrong)

Dump formats come from the M1 captures (`tests/fixtures`). These were checked against the android-16.0.0_r4 sources
but not yet seen on the device, so a mismatch shows up as INCOMPLETE: `mForceHiddenFlags=<decimal>` in the task block
of `dumpsys activity activities` (TaskFragment.dump, printed only when hidden), `dumpsys dropbox --print <tag>` (header
`Drop box contents: N entries`, entries `<yyyy-MM-dd HH:mm:ss> <tag> (...)` followed by the unindented text),
`CredentialType: PIN|PASSWORD|PATTERN|NONE` in `dumpsys lock_settings`, `mRecentsComponent=` in
`dumpsys activity recents`, `am stack remove <task>` (removal verified in the containers dump) and
`wm dismiss-keyguard` to show the bouncer. The uiautomator dump is only a fallback for the probe home buttons when the
probe's `targets` event is no longer in the log buffer.

## Tap targets and broken state

- Taps on a probe task use `targets` positions only inside its visible band: below its top bars and above its bottom
  bar or the keyboard (from the task's latest `insets` event). A control scrolled away (a synthetic edge swipe that
  is not taken as a gesture scrolls the probe) or covered by the keyboard is first dragged into view slowly (no
  fling); DuoProbe **gate-3** reports the new position after the scroll. With gate-2 such a tap is INCOMPLETE ("DuoProbe
  gate-3 needed") instead of landing on the keyboard or off screen.
- Every probe task launched or restored from the home, and the other panel's task in Home and Back checks, must stay
  reachable by input at its panel: the input dispatcher lists its window with touchable flags, frame = panel and
  touchable region = panel (`<empty>` or partial -> FAIL, a region format not understood -> INCOMPLETE). Back also
  requires the gestured task not to be left transformed. After every Home/Back repetition (and its clean-up relaunch)
  the pair is checked the same way; a broken pair is saved (`extra/*-broken-window.txt`, `*-broken-wmshell.txt`) and
  re-created so later repetitions do not inherit it. A definite defect **fails that repetition**; evidence that could
  not be judged (e.g. an unknown touchable-region format) makes it INCOMPLETE and never turns a FAIL into anything else.
- A tap or scroll drag is never sent outside the requested panel: bounds that do not intersect it are refused before
  any input, and both drag endpoints must lie in its visible content band.
- Probe home positions: the home logs `targets` only when its layout changes, so on a home that has been running for
  a while the event can be gone from the log buffer. The uiautomator fallback only sees the focused window (it works
  right after Home, not once a probe task has focus), so positions found once in a run are kept. Positions from either
  source (a `targets` event or uiautomator) are only used if no home `onCreate`, `layout`, `onConfigurationChanged` or
  `onDestroy` came after them; a newer `targets` event replaces them. Each fallback writes
  `extra/home-targets-uiautomator-<n>.txt` (control names and bounds, or the dumped window's packages; never text).
- Minimize evidence accepts the policy's reasons `Home`, `Home from Recents` and `Recents #<n>` (M2.2, fw 0018);
  `DuoRecents` lines are kept in `logcat.txt`.
- PO dismisses a non-secure keyguard after each of its reboots (recorded in `preconditions.keyguard_after_reboot`); with
  a secure lock it asks the operator, and without one the PO checks are INCOMPLETE (the properties are still restored).

## Offline tests

```sh
cd tools/duo-gate
uv run --no-project python -m unittest discover -s tests -v
```

Parsers run against real Duo 1 captures; `tests/sim.py` renders dumps in the same r4 formats and simulates a two panel
device behind a fake adb, so whole gates run offline. Test-the-tester cases: wrong panel, stale evidence before the
marker, missing events, ambiguous task identity, tap on the wrong button, reuse creating a new task, Home minimizing the
focused instead of the gestured panel, Back acting on the focused panel, touch/text reaching the other task, a probe
without touch logging, keyguard leaks (visible, touchable, WM or input focus, input delivered, unreported visibility),
rotations that do not happen, operator fallbacks that must not PASS, unparsable dumps, lost device, Ctrl-C and failed
cleanup still restoring, panel properties restored (reboot only when authorized), missing or zero repetitions, manual
checks, PIN redaction, no raw UI hierarchy stored.
